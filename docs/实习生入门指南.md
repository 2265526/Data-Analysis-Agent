## 第 0 章：一句话先看懂这个项目

**这个项目是个「用嘴就能查数据的机器人」。**

业务人员不用会写 SQL，只要在网页上输入一句大白话，比如：

> 统计最近 7 天各品类销售额，对比上周变化

系统就会自动完成以下 4 件事，最后吐出一份带图表的分析报告（PDF / 网页看板）：

1. **听懂需求**（要查什么）
2. **自己写 SQL**（怎么写查询）
3. **安全地执行**（真去数据库查，但只准读、不准改）
4. **生成报告**（把数字变成图表和结论）

整个过程由 **5 个「智能体」接力完成**：`Supervisor → Planner → Coder → Executor → Reporter`。这就是所谓的「多智能体（Multi-Agent）」架构——把一个复杂任务拆给多个 AI 角色，各管一段，像流水线一样。

**你只需要记住三个关键词**：
- **LangGraph**：编排这些智能体的框架（Python 库）
- **多智能体**：5 个 AI 角色接力干活
- **安全只读**：AI 写的 SQL 只能查询，绝不允许改数据

## 第 2 章：一次请求的完整旅程（理解项目的钥匙）

**这一章最重要。** 看懂一次请求怎么从「一句话」变成「报告」，整个项目就懂了一半。

### 2.1 总览：数据流向

```
前端网页
   │  POST /api/v1/tasks  {query: "统计最近7天..."}
   ▼
FastAPI (main.py → src/api/routes.py)
   │  创建 Task 记录 → 丢给后台执行
   ▼
src/graph.py 的 execute_task()
   │  启动 LangGraph 状态图
   ▼
supervisor ──► planner ──► coder ──► executor ──► reporter
   │             │          │           │            │
  意图路由      拆解步骤    写SQL      安全执行      生成报告
   ▼
static/reports/YYYY/MM/DD/{task_id}.md / .pdf / board.json
```

### 2.2 逐段走读（跟着代码走一遍）

**① 前端发请求**
`web/src/views/analysis/Index.vue` 里的 `send()` 调用 `submitTask(query, sessionId)` → `POST /tasks`。

**② 后端接收**
`src/api/routes.py` 的 `submit_task()`：
- 先做**闲聊拦截**（`chat_gate.is_chitchat`），「你好」这类直接返回，不建任务。
- 否则 `_create_task()` 在 `tasks` 表插一条记录，状态 `pending`。
- 把任务丢给后台（默认 FastAPI `BackgroundTasks`，也可切 Celery）。

**③ 执行流水线**
`src/graph.py` 的 `execute_task(task_id)`：
- 读任务 → 检查是否已取消 → 设 `running`。
- 构建**初始状态** `initial_state`（一个 dict），包含 `user_query`、`task_id`、还有**多轮对话上下文**（如果你在同一个会话里连续追问，这里会带上历史，见第 7.7 节）。
- 用 `graph.stream(initial_state)` 一步步跑图。

**④ 五个节点接力**（每个节点都是个纯函数，输入状态、输出要更新的字段）：

| 节点 | 干什么 | 关键产出 |
| --- | --- | --- |
| `supervisor` | 判断这句话是「分析任务」「直接出报告」还是「闲聊」 | `route`（planner/reporter/FINISH） |
| `planner` | 把需求拆成步骤清单 | `plan`（list，每项含 step/依赖/所需表） |
| `coder` | 为当前步骤写 SQL | `code` |
| `executor` | 只读校验后真去数据库执行 | `exec_result`（结果文本） |
| `reporter` | 把结果变成报告 | `final_report`（产物路径） |

**⑤ 落库 + 前端轮询**
每个节点跑完，`graph.py` 把进度写回 `tasks` 表；前端每 2 秒轮询 `GET /tasks/{id}/status` 刷新进度条，完成后拿到报告正文渲染。

### 2.3 三个关键机制（先有个印象，后面详解）

1. **状态（State）**：所有节点共享同一个 dict（`PipelineState`），靠它传递数据。这是理解 LangGraph 的核心。
2. **断点恢复（Checkpointer）**：如果任务在「人工审批」处挂起，整个图的状态会存进数据库，审批通过后从断点继续，不会重跑。
3. **人机协同（interrupt）**：遇到敏感表 / 大结果集，`human_approval` 节点会「暂停」，等真人批准。

## 第 4 章：五个智能体节点详解

每个节点都是一个**纯函数**：`def xxx_node(state: PipelineState) -> dict`，输入完整状态，返回「要更新的字段片段」。它们不直接读写数据库（那是 `graph.py` 和 `utils` 的事）。

### 4.1 Supervisor（路由员）

**职责**：判断用户这句话属于哪类，决定下一步去哪。

- 用**便宜模型** `qwen-flash` 做三分类（省钱，因为输入多输出少）：
  - `planner`：需要拆解执行的分析任务
  - `reporter`：只需汇总已有结果
  - `FINISH`：闲聊，直接回复引导语，不进流水线
- LLM 不可用时**降级**为默认走 `planner`（不崩）。

### 4.2 Planner（拆解员）

**职责**：把一句话拆成可执行的步骤清单。

- 输出 JSON：`{tasks: [{step, description, dependencies, required_tables}], confidence, questions}`
- **能一条 SQL 搞定的只拆 1 步**（避免重复执行）。
- 两个特殊分支：
  - `confidence < 0.6` 或缺口径 → 路由 `clarifier` 向用户提问（如「留存率的分母是什么？」）
  - 预估成本超上限 → 路由 `human_approval` 人工审批
- 有「结果缓存」：同一个需求（且无多轮上下文）直接复用上次的拆解结果，省一次 LLM 调用。

### 4.3 Coder（写代码的）

**职责**：为当前步骤生成 SQL（或少量 Python）。

它生成 SQL 时会注入四样东西，保证写对：
1. **真实表结构**（`schema_provider` 从 PG 读，或 `mcp_client` 按需补精确列）
2. **锁定指标口径**（`metric_registry`，防止它乱写销售额=SUM 错字段）
3. **历史相似成功代码**（`schema_retriever` 从 Chroma 检索，参考别人写对的）
4. **多轮上下文**（`context_window`，如果你在追问「再按华南区筛」）

- **错误分类**：执行失败后，`classify_error` 判断是「语法错」（原地重写）还是「逻辑错」（回 `planner` 重新规划）。
- 最多重试 `MAX_RETRY = 3` 次，超了转人工审批。

### 4.4 Executor（执行者）

**职责**：安全地执行 Coder 写的代码。

- **SQL 三道防线**：
  1. `sql_validator.validate_readonly` 只读校验（黑名单 DROP/DELETE/… + 注释剥离 + 代价预判）
  2. 复杂 SQL 先 `explain_sql` 预检（MCP EXPLAIN，提前发现表/列不存在）
  3. 本地 `psycopg2` 以 `SET TRANSACTION READ ONLY` 执行（**物理上不可写**，双保险）
- **大结果集**（>10000 行）或**敏感表** → 转 `human_approval` 人工审批。
- 执行失败 → 把错误信息还给 `coder` 重写（自修复循环）。

### 4.5 Reporter（写报告的）

**职责**：把执行结果变成 Markdown + PDF + 看板。

- 用 LLM 生成：执行摘要 / 正文 / 数据口径 / 行动建议。
- 自动生成图表（`chart_gen`）、数据明细表、血缘溯源附录（`lineage`）。
- 产物写到 `static/reports/YYYY/MM/DD/{task_id}.md|.pdf|board.json`。

### 4.6 两个辅助节点

- **Clarifier（澄清）**：缺口径时用 `interrupt()` 挂起，向用户提问，用户回答后回 `planner` 重新拆解。
- **HumanApproval（审批）**：用 `interrupt()` 挂起，等真人批准/拒绝；拒绝则任务 `failed`。

## 第 5 章：状态与编排（LangGraph 核心）

### 5.1 状态 `PipelineState`（`src/state.py`）

所有节点共享的 dict，字段包括：

| 字段 | 含义 |
| --- | --- |
| `user_query` | 用户原始需求 |
| `plan` | 拆解出的步骤清单 |
| `current_task_index` | 执行到第几步 |
| `code` | 当前 SQL |
| `exec_result` | 执行结果（大结果集只传摘要） |
| `error_log` | 最近错误（供 Coder 修复） |
| `retry_count` | 重试次数 |
| `route` | 路由目标（节点靠它决定下一步） |
| `human_approval` | 审批结果 |
| `final_report` | 报告产物路径 |
| `session_id` / `conversation_context` | 多轮对话上下文（第 7.7 节） |
| `sub_results` | 并行执行的各步骤结果（`operator.add` 累加） |

### 5.2 图怎么组装（`src/graph.py`）

```python
builder = StateGraph(PipelineState)
builder.add_node("supervisor", supervisor_node)
builder.add_node("planner", planner_node)
# ...
builder.add_edge(START, "supervisor")
builder.add_conditional_edges("supervisor", _route_after_supervisor, {...})
```

- **`add_edge`**：固定顺序（A 完了必去 B）。
- **`add_conditional_edges`**：根据节点返回的 `route` 字段动态决定去哪。
- **路由函数**（`_route_after_xxx`）就是读 `state["route"]` 返回下一步的纯函数。

### 5.3 三个高级机制

1. **Checkpointer 断点恢复**：`get_checkpointer()` 返回 Postgres/内存保存器。任务挂起时整个状态落库，恢复时从断点继续。生产用 Postgres，开发可降级内存。

2. **interrupt 人机协同**：节点内调 `interrupt(payload)` 会让图「暂停」，把控制权交回。审批接口用 `Command(resume={...})` 恢复，`interrupt()` 返回审批结果。这是 LangGraph 官方 HITL 模式。

3. **Send 并行**：`planner` 拆出多个无依赖步骤时，用 `Send("step_exec", {...})` 并发派发，每个子任务独立 `coder→executor`，最后 `aggregate` 汇总。用 `sub_task_id` 防止乱序。

## 第 6 章：数据模型（数据库表）

所有表由 `src/models/*.py` 定义（SQLAlchemy ORM），启动时 `bootstrap.py` 自动建表 + 幂等补列。

| 表 | 文件 | 用途 |
| --- | --- | --- |
| `tasks` | `task.py` | ★ 任务主表：需求/状态/进度/结果路径 |
| `audit_logs` | `audit.py` | ★ 操作日志：每次提交/审批/执行全留痕 |
| `task_node_runs` | `task_node_runs.py` | 每个节点每次运行的 token/耗时/行数 |
| `cost_records` | `cost_records.py` | 成本明细（预估/实际） |
| `query_runs` | `query_run.py` | SQL 血缘：每条 SQL 涉及表/行数/耗时 |
| `metric_definitions` | `metric_definition.py` | ★ 指标语义层：锁定口径 |
| `chat_sessions` | `chat_session.py` | 会话（多轮对话） |
| `chat_messages` | `chat_session.py` | 会话消息（含报告快照） |
| `users` | `user.py` | 用户与角色 |
| `model_routes` | `model_routes.py` | 节点→模型→单价→优先级 |

**关键关系**：
- 一个 `task` 关联多条 `task_node_runs`、`cost_records`、`query_runs`、`audit_logs`（都靠 `task_id`）。
- 一个 `chat_session` 关联多条 `chat_messages`（`ON DELETE CASCADE`）。
- 删除任务会级联删掉它的运行明细和成本（外键 `ON DELETE CASCADE`）。

> 想了解全量字段，看 `data/数据库设计.docx`。

## 第 7 章：工具层与横切关注点

### 7.1 SQL 只读校验（`sql_validator.py`）

安全的第一道闸。核心函数：
- `strip_comments`：去注释（**感知字符串字面量**，不会把 `'a--b'` 里的 `--` 当注释——这是我们修过的 bug）。
- `validate_readonly`：黑名单关键字（DROP/DELETE/INSERT/UPDATE/…）+ 多语句拦截 + 代价预判。
- `check_query_cost`：拦 `pg_sleep` 等高危函数、笛卡尔积、无 LIMIT 全表扫描。
- `find_sensitive_tables`：识别 `customers`、`user_phone_records` 等敏感表 → 触发审批。

### 7.2 指标语义层（`metric_registry.py`）

解决「同一个『销售额』不同人算出不同数字」的口径漂移问题。把指标口径（聚合方式 + 表达式 + 过滤条件）固化进 `metric_definitions` 表，Coder 生成 SQL 时注入目录，**只能选用、不能自己发明**。

### 7.3 表结构（`schema_provider.py` / `schema_retriever.py` / `mcp_client.py`）

- `schema_provider.fetch_schema_sql()`：连 PG 读真实表结构，大表展开前 12 张（防上下文爆炸）。
- `schema_retriever`：Chroma 向量检索历史成功代码（负向过滤：只要 `status=success`）。
- `mcp_client`：通过 MCP SDK 连 `postgres-mcp`（只读），复杂 SQL 做 EXPLAIN 预检、按需批量取表结构。不可用自动降级。

### 7.4 模型分级路由（`model_router.py` + `settings.py`）

省钱策略：**贵的模型干难的活，便宜的干杂活**。

| 节点 | 模型 | 原因 |
| --- | --- | --- |
| supervisor / aux（错误分类/摘要） | `qwen-flash` | 简单任务，便宜够用 |
| planner / coder / reporter | `deepseek-v4-flash` | 核心推理，需要强模型 |

还支持**主备切换**：主模型连续失败自动切备选。

### 7.5 结构化输出（`structured_json.py`）

让 LLM 稳定吐 JSON 的辅助。因为 `deepseek-v4-flash` 不支持 `response_format=json_schema`，所以改用「提示词约束 JSON + 文本解析 + Pydantic 校验」。所有 LLM 节点都走 `invoke_structured()`。

### 7.6 安全工具（`security.py`）

- `mask_phone` / `mask_id_card` / `mask_sensitive`：手机号/身份证脱敏。
- `encrypt` / `decrypt`：AES-256-GCM（加密检查点快照）。
- `hash_password` / `verify_password`：PBKDF2 口令哈希。

### 7.7 多轮对话上下文管理（`context_window.py`）—— 较新功能

让「再按华南区筛一下」这种**追问**能被理解。三层结构：

- **L1 固定层**：各节点 system prompt + 指标目录（节点内拼接）
- **L2 滑动层**：最近 N 轮原始消息
- **L3 压缩层**：更早历史摘要（qwen-flash 压缩）+ 累积筛选条件（规则提取 + LLM 兜底）

入口在 `graph.execute_task()` 里 `build_context_raw()` 读一次历史，各节点用 `format_context()` 按预算裁剪注入。相关表：`tasks.session_id` + `chat_messages`。

### 7.8 其他横切模块速览

- **`logger.py`**：structlog 结构化日志，自动脱敏。
- **`metrics.py`**：进程内 Prometheus 指标，`GET /metrics` 暴露。
- **`rate_limit.py`**：令牌桶限流（LLM 调用 20 次/分钟）。
- **`circuit.py`**：熔断器（LLM 连续失败就短路）。
- **`costing.py`**：成本预估，超预算转审批。
- **`cache.py`**：Redis 结果缓存（planner/coder 复用）。
- **`notifier.py`**：审批通知（默认打日志）。
- **`intent.py`**：解析意图（时间窗口/同比/趋势），决定报告要不要画趋势图。
- **`lineage.py`**：从 SQL 提取涉及表，落 `query_runs` 做血缘溯源。

## 第 8 章：安全机制（重点，面试常考）

### 8.1 SQL 三层防护（纵深防御）

1. **应用层校验**：`validate_readonly` 黑名单 + 注释剥离，先拦一波。
2. **数据库层只读**：`SET TRANSACTION READ ONLY`，即使校验被绕过也写不进去。
3. **沙箱隔离**：Python 代码跑在 Docker 容器里（无网络、非 root、CPU/内存受限、30s 超时、用完销毁）。

### 8.2 数据脱敏

- 日志、审计里的手机号/身份证自动打码。
- 敏感表（`customers` 等）查询强制人工审批。

### 8.3 审计合规

`audit_logs` 记录每次请求的输入输出、操作者、IP、审批人、时间，前后状态快照。满足等保/GDPR 追溯。

## 第 10 章：如何改代码（动手练习）

### 10.1 想加一个新节点

1. 在 `src/nodes/` 新建 `mynode.py`，写 `def mynode_node(state) -> dict`。
2. 在 `src/nodes/__init__.py` 导出它。
3. 在 `src/graph.py`：`add_node("mynode", mynode_node)` + 加边。
4. 在 `src/state.py` 补充需要的字段。
5. 写 `tests/unit/test_mynode.py`。

### 10.2 想加一个新工具

在 `src/tools/` 新建文件，暴露纯函数，节点里 `from src.tools.xxx import ...` 调用即可。

### 10.3 想加一个数据库字段

1. 在 `src/models/*.py` 加 `mapped_column(...)`。
2. `bootstrap.py` 会幂等补列（或跑 `python scripts/migrate_db.py`）。

### 10.4 想改提示词

找到对应节点的 `_SYSTEM_PROMPT` 字符串直接改；如果改了 planner 的拆解策略，记得 bump `PLAN_CACHE_VERSION`（否则旧缓存不会失效）。

### 10.5 想加一个配置项

在 `src/utils/settings.py` 加字段（自动从 `.env` 读），代码里 `settings.xxx` 取用。

## 第 11 章：常见坑（前人踩过的）

1. **`uvicorn --reload` 必须带 `--reload-dir src`**：否则会监视 `.venv`，装了 mcp 等几百个包后一有变化就无限重启。
2. **节点失败分支返回 `status` 用 `running` 不用 `failed`**：中间重试若返回 `failed`，前端会误当终态停止轮询。
3. **结构化输出别用 `with_structured_output`**：`deepseek-v4-flash` 不支持 `response_format`，要用 `invoke_structured`（提示词约束 + Pydantic 校验）。
4. **MCP 每次调用都起子进程**（~1-1.5s）：简单 SQL 别做 EXPLAIN 预检（用 `is_complex_sql` 判断），多表用 `get_table_details_batch` 一次取完。
5. **大结果集别塞进状态**：只传摘要（`executor` 里 `summarize_output`），否则上下文爆炸。
6. **多轮上下文下要跳过 planner/coder 缓存**：否则不同会话的追问会命中错误缓存（已处理）。
7. **改提示词要 bump 缓存版本号**，否则旧缓存命中。
